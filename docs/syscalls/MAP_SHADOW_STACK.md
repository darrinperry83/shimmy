# `map_shadow_stack` (ARM64 syscall 453): GCS protection blocker

This syscall is part of Linux AArch64 Guarded Control Stack (GCS), not merely an x86 feature. The kernel's [AArch64 GCS documentation](https://docs.kernel.org/arch/arm64/gcs.html) says support is advertised by `HWCAP_GCS`; `map_shadow_stack()` then allocates memory with special control-stack access semantics and optional top marker/cap token. GCS enablement, thread inheritance, signals, and faults also involve `PR_*_SHADOW_STACK_STATUS` and architecture state.

Shimmy does not advertise `HWCAP_GCS` in its guest initial aux vector (`src/bootstrap.c`) or `/proc/self/auxv` (`src/syscalls.c`). `src/syscalls_ext.c` has no #453 handler, so the current guest result is `ENOSYS`. Its `prctl` switch has no GCS status controls. Ordinary `mmap` memory is writable by ordinary stores and lacks GCS call/return enforcement, so returning it from #453 would falsely claim a protection mechanism. A marker/token written into plain memory would not repair that. Keep `ENOSYS` until Shimmy can implement the protected memory and per-thread execution contract; the test in this branch verifies the current, explicitly unsupported behavior, not syscall compatibility.

A real implementation would require GCS-equivalent instruction and memory protection on the executing hardware or a complete instruction/memory trap layer, correct token/marker layout, virtual thread state and `prctl`, clone/exec/signal/ptrace behavior, and matching `HWCAP_GCS` advertising only after all of those work. Test in a disposable ARM64 guest with a Linux GCS oracle: both accepted flag combinations and rejection paths, inability to modify GCS pages with normal stores, call/return mismatch faults, signal return, and child thread inheritance. No such protection is demonstrated in this branch.
