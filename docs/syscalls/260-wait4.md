# `wait4` (#260): bounded guest child waits

The core dispatcher handles this syscall. A positive PID is accepted only
when Shimmy's guest-child registry issued it. For `pid == -1`, Darwin's
`waitid(P_ALL, ..., WNOWAIT)` peeks before reaping; only an observed registered
guest child is passed to `wait4`. Group selectors (`pid == 0` or below `-1`)
return `EOPNOTSUPP` because there is no complete guest process-group registry.
Unknown positive children return `ECHILD`.

Only Linux `WNOHANG`, `WUNTRACED`, and `WCONTINUED` options are translated.
Other option bits return `EINVAL`. Status and Linux-layout rusage outputs are
checked for guest writability before a child can be reaped. No-event returns
leave these outputs unchanged. The existing Darwin-to-Linux rusage conversion
is preserved.

This is not full Linux wait compatibility. A host helper child that becomes
the first pending `P_ALL` event causes `EOPNOTSUPP` rather than being reaped;
that can delay a different guest child. Concurrent reapers can race between
the non-consuming peek and the targeted wait. The guest child registry is
bounded, shared through a boot-token file, and does not model every namespace
or process group. Signal status translation beyond ordinary exits is not
validated by this probe.

Verification: `./build.sh cli` and `python3 tests/run-wait4.py` pass for an
ordinary guest. The ARM64 probe covers unknown PIDs, unsupported options and
groups, bad output pointers before reaping, a known child, exit status and
rusage output. A private Arch boot gate belongs to the integration batch.
