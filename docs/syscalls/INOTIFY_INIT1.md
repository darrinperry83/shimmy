# `inotify_init1` (ARM64 syscall 26): watched-file event increment

The existing inotify descriptor is a pollable pipe. Before this increment, `inotify_add_watch` stored a watch identity and `inotify_rm_watch` produced `IN_IGNORED`, but changes to the watched file produced no notifications.

Each added watch now opens its resolved host path with `O_EVTONLY` and subscribes to Darwin vnode events on an instance-local kqueue. The kqueue and watched-file descriptors are reserved from guest fd cleanup. A worker writes Linux wire-format `IN_MODIFY`, `IN_ATTRIB`, `IN_DELETE_SELF` or `IN_MOVE_SELF` events to the pipe when the corresponding mask is requested. The writer suppresses `SIGPIPE` if a guest has closed its read aliases. Deletion also emits `IN_IGNORED` and removes the watch; rename leaves the watch attached. A per-instance cap of 128 watches prevents unbounded watch descriptors, and the worker starts only when the first watch is added. This is an event path for watched files, not full Linux inotify compatibility.

Limits: directory child-name `IN_CREATE`/`IN_DELETE` and move-cookie events are not implemented; a directory watch can still be registered but does not provide those semantics. Linux queue-overflow reporting, fork inheritance, final-close teardown, and full watch-mask validation are also pending. Fork handlers prevent inheriting a locked state mutex, but the child has no worker thread; adding a new watch to an inherited instance returns `EOPNOTSUPP`. The backend uses one worker per active inotify instance, so it needs a process-level lifecycle and resource-budget review before production. No claim of complete #26–28 support follows from this increment.

`sh tests/run-inotify-file-events.sh` checks host watched-file write/delete events, removal, and worker termination on an invalid kqueue. `sh tests/run-inotify-file-guest.sh` checks ARM64 guest init, add-watch, poll/read, duplicate descriptor, write, deletion, and implicit watch removal. The earlier `sh tests/run-inotify-rm-watch.sh` regression passes. A private Arch clone made with `rsync --no-perms` failed at `Failed to start up manager` on both the unmodified `8f2b019` baseline and this branch, so that comparison is inconclusive about the branch's boot behavior. A valid private Arch boot gate remains required before integration.
